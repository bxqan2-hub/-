## Finding → Path → 复现

**Finding 1：验证码和时间来自不同层。** 相关邮箱实际 GET 返回 HTTP 200，结构为：

```json
{"success":true,"data":{"body":"MAIL_BODY","code":"OTP","date":"RFC_2822_DATE","subject":"SUBJECT"},"message":"OK"}
```

旧 `_extract_structured_api_code` 的 `_flatten_json(data)` 能搜到 `data.code` / `data.body` 内的验证码，而 `data.get("date")` 只检查外层，因此 `received_at/msg_ts/subject` 丢失。`fetch_latest_otp` 的统一时间门禁依赖 `msg_ts`，在空历史快照下没有新旧依据却接受候选。

修改同一函数：确认 JSON 是字典后，若 `data` 是字典就选定该单邮件对象，然后沿原字段优先级解析 code/date/subject。时间和验证码始终同源，不将外层 API 请求时间拼到内层邮件上，不增加递归或跨邮件搜索。

**复现顺序：** 空历史快照 → 返回请求前 45 秒的嵌套 RFC 2822 邮件 → 稍后返回新邮件 → 只提交新码并确认密码。持续返回旧邮件时，在原预算内退出且没有密码输入/OTP 提交。另覆盖相同外形的正文提码、错误历史快照、外层干扰码/日期、两秒容差和真实日志脱敏。

**只读真实响应对照：** 在内存编译当前 HEAD 的旧解析函数，与修后函数处理同一份响应。Job 355/358 均得到：旧 `msg_ts=None`，新时间可解析，OTP 相同；以邮件时间后 3 秒为过滤边界，旧函数仍接受，新函数排除。新函数分别解析到本地时间 11:55:03 / 11:54:47。

这些当前 GET 响应验证了解析器缺陷及修复，并非失败瞬间的网络录包。历史 OTP 已脱敏，故不声称已逐条证明四次 401 提交的数字完全等于注册旧码；旧信误判是已复现的代码缺陷，也是与日志链最吻合的原因。

**Finding 2：Session 403 独立问题。** 路径为 `_PASSWORD_REAUTH_JS/_PASSWORD_REAUTH_SELENIUM_JS` 的首个 Session GET → `_setup_password_with_driver` 返回 `password_reauth_start_failed`。现有终态已经保留子阶段；未取得响应头/挑战正文的现场证据，尚未细分边缘拦截与应用鉴权拒绝，不在本轮扩大重试或绕过身份校验。

## 密码 / 2FA 安全复核

- **密码确认**：`_setup_password_with_driver` 仍等待页面成功终态；`_setup_2fa_result` 成功后才保存密码 checkpoint。旧邮件持续返回的回放不提交 OTP、不填写密码；原未确认密码不落盘测试通过。
- **身份与会话**：`_assert_authenticated_account`、重认证 JS 预检邮箱、同窗 Cookie/代理、补密码后重新读取当前 Token 保持不变；账号错配测试阻断写入。
- **Secret 保存**：`_setup_totp_with_driver` 仍复用同一 enrollment，只在 activate `success is True` 后调用 `_persist_activated_totp_checkpoint`；模糊写入结果/400 不重放，相关测试通过。
- **只读失败分离**：Session 403 在密码/MFA 前停止；已完成激活后的 `_validate_2fa_token` 失败仍保留确认凭据，不伪报激活失败。
- **凭据暴露**：新测试包含带 OTP 的嵌套 subject，确认已有脱敏继续生效；测试日志无验证码、密码和私有邮件链接。未保存真实远端正文或凭据，未变更 SSL/代理/邮箱归属规则。
