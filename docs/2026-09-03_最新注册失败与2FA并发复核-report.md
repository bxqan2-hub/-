# 最新注册失败、Roxy 启动并发与 2FA 复核（2026-09-03）

## 采样范围与结论

- 采样 `注册日志/` 22:20–22:39 的 58 个任务：40 个成功、14 个失败、4 个手动停止。
- 其中 43 个任务进入 2FA，40 个完成 enroll/activate，3 个任务在 2FA 前后失败；Job 74 与 Job 81 使用同一邮箱/账号记录（账号 id=675），所以对应 2 个独立账号，不是 3 个独立账号。
- 2FA 失败不是单一“请求失败”：Job 61 是 Selenium 异步脚本超时，Job 74/81 是密码重认证邮箱验证码已取到但提交动作失败。两类路径分别处理。
- Roxy 启动速度确实被并发资源和生命周期串行锁拖慢；最新 54 条含创建/打开阶段的日志中，`create` 中位数 8.5 s、P90 23 s、最大 56 s，`open` 中位数 23 s、P90 47 s、最大 71 s。代码没有把 workers 改小，主要等待来自 `_ROXY_LIFECYCLE_LOCK` 与本地 Roxy API 15 s 超时重试。

## 高概率原因与修复

### H1：`_safe_get` 把 Selenium script timeout 留在 8 秒

- 证据：`注册日志/c260a2d9-a3a4-43df-a550-f3e257371071.log`（Job 61）在 22:30:09 开始浏览器 MFA，22:30:17 以 `TimeoutException: script timeout` 失败；enroll 前未出现 HTTP 状态或服务端错误。
- 路径：`core/roxy_registration.py::_safe_get` 临时设置 `driver.set_script_timeout(8)`，旧实现只恢复 page-load timeout；后续 `core/account_export.py::_browser_authenticated_json_post` 使用同一个 driver 执行 MFA enroll，因此沿用了 8 秒脚本预算。
- 修复：在同一 `finally` 中恢复 page-load 与 script timeout，避免导航容错设置污染后续 MFA。新增回归用例验证 `[8, 90]` 的设置/恢复顺序。

### H2：密码重认证 OTP 提交存在一次 DOM/renderer 瞬态

- 证据：`注册日志/dacb8f9c-27d3-4d3f-b87b-1df18cae207d.log`（Job 74）和 `注册日志/bee30ac8-f6e7-4390-836f-259d5c65d904.log`（Job 81）均完成注册并成功取到重认证 OTP，随后在 `stage=password_email`、`code=password_email_reauth_submit_failed` 停止；两次是同一邮箱记录，第二次发生在第一次账号落库前后的并发窗口。
- 路径：`core/account_export.py::_setup_password_with_driver` → `_password_submit_code`。原路径一次返回 False 就结束，没有重新定位 OTP 输入框/submit 控件。
- 修复：同一验证码只在第一次提交返回 False 时等待 0.75 秒并重新定位重试一次；仍失败时只记录当前 URL 和可见 code 输入数量，不记录验证码。没有重新取码、切换代理或重复 enroll。

## 中概率原因与处理

- **Roxy lifecycle 排队**：Job 45/46/47/51/53/81 等 `open` 等待 42–71 s；`core/roxybrowser_client.py::request` 对 `/browser/create|open|close|delete` 共用 `_ROXY_LIFECYCLE_LOCK`，并发 10 个可视 Profile 时形成队列。该锁是此前 10 路冷启动造成 Roxy API 超时/整机负载的护栏，本次不直接删除；下一轮应在固定 workers 下采集锁等待、RoxyChrome 工作集、open P50/P95，再决定 2 路 semaphore 或分离 open/close 锁。
- **代理传输/漂移**：Job 48（`stage=proxy_isolation`，预检 IP 与浏览器 IP 不一致）、Job 65（`ERR_SOCKS_CONNECTION_FAILED`）、Job 83（`ERR_CONNECTION_CLOSED`）均在登录页前后失败；这些不是 2FA，应继续分别轮换/隔离代理并保留邮箱。
- **邮箱 OTP 与 callback**：Job 71 的 resend 无 acknowledgement，Job 86 的 Email verified callback 连续返回 OTP，Job 72 进入登录密码页；均未进入 MFA enroll，不能归因于 MFA 接口。
- **密码页推进**：Job 62/64 在两次密码提交观察窗口后仍停留 `/create-account/password`；当前日志没有服务端拒绝字段，仍属于密码页面状态机问题，独立于 2FA。

## 低概率与观察项

- Job 61 的 `within_budget=False`（downloaded=5,059,223、hits=33、misses=7）是页面重资源/渲染负载信号，不是 MFA 响应被缓存。
- 共享缓存只处理明确公共 JS/CSS；`/api/auth/session`、MFA enroll/activate、Sentinel 和认证请求保持实时网络。Job 66–70、73、75/76、78/79、84–91 的 2FA 日志均显示 enroll/activate 完成，说明缓存优化没有造成普遍 MFA 失败。
- Job 74/81 的同邮箱重入暴露出两个独立 WebUI 进程或进程间邮箱 lease 的竞态（Windows 进程列表曾同时出现同命令的父/子 WebUI）；后续应保持 CLI/WebUI 串行，或接入跨进程原子 lease，避免一个账号未完成安全设置时再次领取同一邮箱。

## 与参考项目对照

上游锁定 commit `68a1f8faede7e41f10ac5f9af267465fa61d0e3d` 的 `setup_2fa_from_selenium` 保持同一浏览器网络栈，顺序为 enroll → 读取 `secret/session_id` → 生成 TOTP → activate，并要求 `success` 为真才完成。上游 helper 在没有显式 token 时才读取 `/api/auth/session`；本地 2eedaae 已在补设密码后清空旧 registration token，使 helper 读取同窗新 token，同时保留账号邮箱匹配、Cookie/代理连续性和 checkpoint 边界。本轮新增的 timeout 恢复与一次 OTP 提交重试不改变上游协议顺序。
