## 结论

本站和上游都采用“只拦截 Script/Stylesheet、把一方静态资源按 URL 哈希落盘、命中后通过 DevTools 回放”的思路。两者都不是按账号、Profile 或 IP 分片的缓存，因此同一公共静态 URL 在不同 Profile 中得到相同字节是设计行为；这本身不携带账号 Cookie。

本站当前的缓存安全边界比上游更窄：本站只缓存四类公共静态路径，并检查请求认证头和响应的私有性；上游按一方 Host 加安全路径排除，允许更多未明确标记为安全资源的脚本进入缓存。本站还增加了缓存 schema、body 摘要和大小校验；此前的同 URL miss 协调已在本次风险复核中移除。

上游的优势是同时覆盖 Playwright 与 Selenium，并用每会话随机 refresh salt 打散“全热缓存”访问模式；本站 Roxy/Selenium 路径也保留了 12% 小资源回源策略。本次已移除本站跨 Profile miss 合并，使冷启动回源行为与上游一致；温缓存的公共静态资源仍按 URL 共享。

## 与账号/IP/指纹隔离的关系

### 1. 静态资源缓存

两套实现都把公共 JS/CSS 当作跨会话共享对象。只要资源确实是版本化公共静态文件，字节一致不会让账号 Cookie、Token 或邮箱进入另一个 Profile。风险来自“分类过宽”而不是 URL 哈希本身：若动态脚本或带业务状态的响应被归类为静态资源，URL-only key 就会造成跨 Profile 回放。

本站已将资格判定收窄到四个公共前缀；当前分类器结果为：

```text
https://chatgpt.com/backend-api/sentinel/sdk.js                 False
https://chatgpt.com/cdn-cgi/challenge-platform/x/main.js       False
https://chatgpt.com/sentinel/x/sdk.js                           False
https://chatgpt.com/unauth-mweb/scripts/declarative.js          False
https://chatgpt.com/_next/static/app.js                         True
```

本站现有 2811 个 `.json/.bin` 对中，2725 个 metadata 带 `schema_version=2`，86 个为旧格式；旧格式（包括已发现的非公共挑战/后端条目）会在 `StaticResourceCache.read` 的 schema gate 处返回空，不会继续回放。metadata 敏感头计数为 0，`Vary` 头计数为 0。当前回放还会过滤 `cf-ray`、`report-to`、`date`、`age`、`etag`、`traceparent`、`x-envoy-*` 等边缘/时间头，避免把首个 CDN 响应的动态标识带到其他 Profile；请求侧的重新验证指令不会命中共享缓存，响应 `Vary` 只有 `Accept-Encoding` 可接受，读回 metadata 的状态必须仍为 200，路径中的 dot-segment/反斜杠也会被拒绝。

### 2. Cache miss 协调（本次已移除）

上游未命中时每个并发 Profile 都可独立回源，再以同 URL 原子覆盖缓存。本站原先增加的跨 Profile miss 协调器会让其他 Profile 等待并回放首个结果；本次已删除该类、miss 协调调用和 loading 状态，当前每个 Profile 的 miss 都直接走实时网络。这样消除了最明显的冷启动同步特征；温缓存命中仍是公共静态资源的 URL-only 共享。

### 3. 地理信息缓存

上游 `vendor/.../core/session.py` 的 `_GEO_CACHE` 按代理 URL 缓存出口地理结果。旋转网关复用同入口 URL 时，后续会话可能沿用旧地理结果。

本站 `core/session.py` 在 `require_proxy=True` 时跳过 `_GEO_CACHE`，每个严格代理会话重新探测出口；非严格辅助会话仍按代理 URL 使用进程内缓存。本站这一点更适合旋转出口，但实际注册的 Roxy Profile 仍以 Roxy 自身 `proxyInfo/fingerInfo` 为准。

### 4. Roxy Profile 指纹开关（与静态缓存分开）

上游 `vendor/.../core/roxybrowser_client.py` 会把 `randomFingerprint` 按 `ROXY_RANDOM_FINGERPRINT` 写入 `/browser/create`，配置默认开启，并把 `ROXY_DEFAULT_OS='random'` 解析为桌面系统随机值。本站当前 `create_profile` 没有写入 `randomFingerprint` 字段，只随机 `os`（Windows/macOS）和窗口名；这不是缓存串号，但会影响“缓存安全边界已经收紧后，Profile 本身是否有足够差异”的判断。

### 5. Sentinel SDK 缓存边界

协议模式下，本站会发现远端 SDK 版本并把代码保存为版本化文件；读取时检查版本格式、`SentinelSDK`/`.token` 内容标志和 Node `--check` 语法，写入采用临时文件替换。该文件是程序代码，不是按账号保存的会话数据。上游锁定版本的 vendor Sentinel 实现直接使用随仓库提供的 SDK/逆向逻辑，未见同类动态 SDK 持久缓存。两者都把 Sentinel 请求本身留在实时网络，不能把 SDK 文件缓存误认为 challenge 响应缓存。

## 代理分配边界（非缓存本体，但会改变网络特征）

- 上游 vendor `config/proxy.py` 使用持久游标、跨进程文件锁和可选 `allocation_scope` claim，分配顺序化；上游顶层 `core/proxy_pool.py` 则按成功率排序后轮询。
- 本站 `config/proxy.py` 在 API 关闭时使用 `random.choice(available)`；排除集合是调用方本地集合，没有跨任务出口 IP reservation。
- 因此本站“随机代理”仍可能出现相同真实出口 IP；缓存隔离修复不能替代 IP 唯一性校验。

## 建议优先级

1. 保留本站当前四类公共静态前缀和响应私有性检查，不照搬上游的宽 Host 资格。
2. 保持当前 `secrets.token_bytes(16)` refresh salt 和“每 Profile 独立 miss 回源”行为。
3. 对需要强画像隔离的批次，关闭静态缓存或将缓存根目录按 Profile 分片；当前 URL-only 温缓存仍属于公共资源共享。
4. 对严格一号一出口 IP 的场景，在代理预检返回真实 `exit_ip` 后做全局 reservation；代理 endpoint 去重只能作为辅助。
5. 记录脱敏的 cache hit/miss、refresh、Profile 摘要和出口国家，不记录 Cookie、Authorization、Token、密码或 MFA Secret。
