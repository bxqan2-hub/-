## Findings

### P1：注册任务线程池没有上限，和上游的硬上限脱离（保留的本地优化差异）

路径：[`core/registration_service.py:277`](../core/registration_service.py:277)–[`core/registration_service.py:284`](../core/registration_service.py:284)。本地 `_normalize_workers()` 只做 `max(1, value)`，WebUI 的 `_positive_worker_count()` 也只拒绝小于 1 的值；因此请求 `workers=10000` 会直接构造同规模 `ThreadPoolExecutor`。上游同一模块有 `REGISTRATION_WORKER_LIMIT`，并把结果夹在 1–16 之间。

影响：可视浏览器注册会同时创建大量 Profile/Chrome 进程，造成内存、句柄和代理池耗尽；这与项目近期已经记录的 10 路 Roxy 高峰约 7.9 GB 工作集风险相冲突。现有测试甚至明确接受 `workers=50`，说明该缺口不会被当前回归挡住。

处理决定：本站当前允许调用方按机器资源自行提高并发，已有 WebUI 回归也覆盖 `workers=50`；因此本轮不强行套用上游 1–16 硬上限。它仍是资源耗尽风险，后续若要收敛应直接修改现有 `_normalize_workers()` 并补边界测试，不新增第二个 worker 参数或旁路线程池。

### P1：任务启动前的数据库异常会泄漏活动任务状态（已修复）

路径：[`core/registration_service.py:367`](../core/registration_service.py:367)–[`core/registration_service.py:381`](../core/registration_service.py:381)。`_activate_job(job_id)` 之后，`db.start_pending_job(...)` 在 `try/finally` 之外。如果 JSON 读写、权限或临时文件替换在这里抛异常，函数会直接结束，`_STOP_EVENTS`、`_ACTIVE_JOBS` 和线程局部 `job_id/gc_mode` 不会执行 `_deactivate_job()`。

影响：后续“全局停止”、活动任务计数和停止清理可能把已结束线程当成活动任务；重复提交时还会留下不可回收的停止事件。`_run_codex_retry_job()` 也有同样的结构：`db.get_job()` 和首次 `db.update_job()` 在 `try` 之前（[`core/registration_service.py:524`](../core/registration_service.py:524)–[`core/registration_service.py:535`](../core/registration_service.py:535)）。

修复：`_run_one_job()` 和 `_run_codex_retry_job()` 现在在调用 `_activate_job()`、读取任务和首次状态更新时捕获异常，先执行 `_deactivate_job()` 再由现有异常处理逻辑写入失败终态，由现有 Future 看门狗收敛任务。新增回归覆盖数据库异常时线程局部状态、活动任务和停止事件均清空。

### P1：`_enqueue_checkout_kind_after_registration()` 是死路径，自动检测功能不会触发（已清理）

路径：函数定义在 [`core/registration_service.py:367`](../core/registration_service.py:367)，仓库检索只有定义，没有任何调用点；成功分支 [`core/registration_service.py:423`](../core/registration_service.py:423)–[`core/registration_service.py:434`](../core/registration_service.py:434) 只更新任务状态，没有调用该函数。`checkout_kind_service` 当前由 WebUI 的显式批量接口调用。

影响：函数名、日志和注释暗示“注册成功后自动开始 Checkout 类型查询”，实际注册成功不会自动入队，形成“代码堆积 + 行为缺失”。

修复：当前产品只提供 WebUI 显式 Checkout 检测，因此已删除这个无调用点的私有函数及其日志路径；现有手动入口不变。删除后仓库源码和测试中不再有该符号，报告中的旧引用仅作为审计记录保留。

### P2：配置热加载承诺与静态导入不一致（OTP settle 已修复，其他常量待收缩）

路径：[`config/__init__.py:232`](../config/__init__.py:232)–[`config/__init__.py:271`](../config/__init__.py:271) 声称 `reload_all()` 让运行时代码看到新值，但 [`core/session.py:15`](../core/session.py:15)–[`core/session.py:20`](../core/session.py:20)、[`core/outlook_client.py:40`](../core/outlook_client.py:40)–[`core/outlook_client.py:46`](../core/outlook_client.py:46)、`core/chatgpt_auth.py`、`core/sentinel.py`、`core/openai_auth.py`、`core/sms_provider.py`、`core/jp_trial_service.py` 仍把常量用 `from config import ...` 绑定到模块加载时的旧对象。只有 `config.<子模块>.KEY` 形式才会随 reload 读取新值。

影响：WebUI 修改配置后，同一进程中部分请求使用新值、部分请求继续使用旧值，尤其是 UA/TLS、邮箱 API 地址、OTP settle 参数和协议常量，难以从日志判断。

附带缺口：`config/email.py` 定义了 `OTP_SETTLE_SECONDS = 5`，但 `apply_env_overrides()` 的 schema（第 173 行）没有该键；即使设置同名环境变量也不会覆盖它。复现结果为：`env_loader.env_int('OTP_SETTLE_SECONDS', 5)` 返回 99，而 `importlib.reload(config.email)` 后仍为 5。

修复：`OTP_SETTLE_SECONDS` 已加入 `config/email.py` 的现有环境覆盖 schema，Outlook settle 默认值改为读取 `_email_cfg.OTP_SETTLE_SECONDS`；新增热加载回归。其他静态导入仍列为后续收缩项，不在本次扩大范围。

### P2：同一业务流程存在多份近似实现，修复容易漏同步

证据：

- `core/roxy_registration.py` 同时包含邮箱输入稳定化、OTP 提交/重发、密码页提交、Session 获取和回调恢复；`core/browser_use_registration.py` 另有一套邮箱/OTP/密码/资料页实现；`core/cloakbrowser_registration.py` 通过导入 Roxy 辅助函数混合第三套驱动语义。
- `core/account_export.py` 的 `_setup_2fa_result()`（[`core/account_export.py:1791`](../core/account_export.py:1791)–[`core/account_export.py:2048`](../core/account_export.py:2048)）单函数约 258 行，同时负责密码前置、浏览器 MFA、协议重认证、OTP 取码、Secret checkpoint 和只读校验；`setup_2fa_result()`、`setup_2fa()`、`maybe_setup_2fa_result()`、`maybe_setup_2fa()` 又提供多层兼容包装。
- `core/roxy_codex_oauth.py`、`core/browser_use_codex_oauth.py`、`core/codex_oauth.py` 分别复制了浏览器 OAuth/OTP 控制逻辑，只有驱动适配差异。

影响：同类页面变化需要改多处；一个分支修复后，另一个分支可能继续使用旧的提交/重试策略。`setup_2fa()` 与 `maybe_setup_2fa()` 在生产代码中没有调用点，只有定义和测试调用，属于兼容 API 候选，不应继续扩展。

只改方案：按“入口 → 状态机 → 驱动适配 → 持久化”拆边界，先画调用图，再移动原实现并在同一改动删除源实现（遵守 R3）；兼容包装要先标记删除条件和时机，不能无限保留。

### P2：跨进程出口 IP reservation 仍未共享

项目既有审计已确认：[`config/proxy.py`](../config/proxy.py) 的 reservation 只在单个 Python 进程内生效；`core/roxybrowser_client.py::open_profile` 和 `core/roxy_registration.py::_verify_registration_exit_geo` 能防住同进程冲突，但多个 CLI/WebUI 进程之间没有共享 lease。项目规则已经要求在共享 lease 接入前串行运行多个进程。

影响：同时启动两个 WebUI/CLI 时，两个进程仍可能拿到同一出口 IP；这不是邮箱、浏览器或 MFA 请求失败，必须单独按 `stage=proxy_isolation` 处理。

只改方案：接入共享、原子、带 owner 和过期时间的 lease 存储后，再放开多进程；在此之前保留 fail-closed 和串行限制，不要通过增加重试掩盖冲突。

### P3：迁移兼容代码长期驻留，启动成本和审计面扩大

路径：[`core/db.py:4709`](../core/db.py:4709)–[`core/db.py:4779`](../core/db.py:4779)。每次启动/初始化都会扫描旧 SQLite、`accounts/*.json`、旧 Outlook 文本和 `outlook_accounts_used.json`；当前仓库同时保留 JSON/TXT、旧 `data/` 和多种邮箱池格式。迁移函数本身是幂等的，但历史目录没有明确删除条件。

影响：数据量大时启动会重复扫描；旧格式解析分支和当前格式同时维护，增加重复账号、状态覆盖和敏感数据误读的审计面。

只改方案：记录一次迁移完成标记，确认现存用户数据已迁移后删除旧读取分支；在删除前保留可验证的迁移报告，不复制项目树或备份目录。

## 建议的只改不堆执行顺序

1. 保持当前并发设计，同时采集机器资源和 Profile 启动指标；有证据后再修改现有 `_normalize_workers()`。
2. 把两个任务入口的启动状态纳入 `finally`，补数据库异常回收测试。
3. 决定 Checkout 自动检测契约，调用或删除死函数，不能保持假路径。
4. 明确热加载契约，逐个替换静态配置导入；每替换一处立即 grep 旧符号并删除死引用。
5. 最后处理流程合并和迁移清理。每次只改点名文件，保留明确的 `+X / -Y` 统计。
