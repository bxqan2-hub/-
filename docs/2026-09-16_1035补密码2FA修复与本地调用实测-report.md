检查前按高/中/低概率分别提出浏览器后端/启动参数、Session/代理/OTP、密码或 MFA 服务端失败；得到阶段证据后，优先检查重复 Session GET 的请求差异，再检查代理/页面状态，最后才考虑本地组件兼容性。

- 登录 helper 的 Session GET 使用 `cache: no-store` 和请求 `cache-control: no-cache`，原补密码 Session/CSRF GET 没有这些设置。现对齐两种浏览器脚本，避免依赖旧的认证读取缓存；不改变请求顺序，不增加重试，不省略账号匹配。
- **历史 403 的缓存/代理/服务端来源没有完整响应头证据。** 请求差异是已确认的实现缺口，本次修复后同账号成功；一次成功不证明缓存是历史 403 的唯一原因。Node 缓存 fixture 用于验证请求契约，不充当真实服务端缓存取证。
