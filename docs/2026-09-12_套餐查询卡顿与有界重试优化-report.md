# 套餐查询卡顿与有界重试优化（2026-09-12）

## 结论与证据

本轮针对账号页自动/手动/批量套餐查询，不修改注册、密码、MFA 或支付写操作。先核对现有选路、运行配置、日志、队列和数据库状态，再进行两次只读套餐 GET 对照及本地回归。

### 原因分档

- **高概率，已证实**：`core/plan_check_service.py::_run_plan_check` 强制传 `max_attempts=0`，忽略用户有限次数配置；`core/chatgpt_plan.py` 的 0 表示无限循环。单次 30 秒、退避逐步增长到 30 秒，慢线路重复占用 worker。账号 worker 另有 `db.get_account/_decorate_account` 约 120 秒陈旧保护，因此它并非永远不退出，而是常常拖到陈旧/停止状态才结束；通用探针没有这个数据库保护。
- **中概率，已证实存在但非全局固定代理**：当前 VN 池为 100 条不同配置，共用一个网关 host:port；PH/JP/VN 各 100 条、ID 20 条。选路函数本来就在当前国家内洗牌轮转，重试也重新选择。相同的脱敏网关摘要不代表同一代理凭据，更不证明出口 IP 相同。
- **低概率，证据不足**：套餐权益 API 本身普遍失效、数据库锁死或线程死锁。21:32:20 时 95 个账号中 84 成功、9 失败、2 running；21:37:09 为 102 个账号中 91 成功、11 失败，没有账号后台活动标记，说明其他账号仍在持续完成。

## Finding → Path → 修改

1. **次数配置失效** → `core/plan_check_service.py::_run_plan_check`：移除强制 `max_attempts=0`，由既有配置生效。
2. **无限循环占用 worker** → `core/chatgpt_plan.py::_plan_check_settings/check_account_plan`：原循环改为有界 range，默认 3 次，允许 1–5 次；旧值 0/负值按 3 次处理，不再进入无限分支。原结果字段 `attempt_count/max_attempts/retry_until_result` 保留兼容读取，后者固定 false。
3. **仅首轮限速** → `_run_plan_check::_retry_proxy`：每次重试也走已有全局 rate slot；使用原国家检测池轮换，日志只记录 account_id/changed/country，不泄露完整代理。显式代理覆盖仍保持其语义，不暗中换成注册代理；空池仍直连，不调用注册动态代理 API。
4. **退避期停止不及时** → `check_account_plan`：带 continue callback 时以 0.25 秒小段等待，停止后不再发下一次请求。正在进行的网络请求仍由单次 timeout 结束，不宣称瞬间中断。
5. **网络错误混报/泄露原文** → `_format_plan_request_error`：TimeoutError、curl 28、TLS/curl 35 分开；其余只保留异常类。主探针 debug 不再输出原始异常/traceback。
6. **默认及当前配置** → `config/proxy.py`、`.env.example`、`webui/config_editor.py`：默认 15 秒/次、3 次；同步两项帮助文案。当前 `.env` 仅修改这两个键，其余字节核对一致，不进入 Git。

默认账号快速路径三次全部耗尽请求预算时，为 45 秒网络时间 + 1.5/3 秒退避，即约 49.5 秒；另加全局限速排队及调度/落库开销。若服务端返回 Retry-After、用户设置更高 timeout 或请求非 fast fallback，则实际总耗时会更长，49.5 秒不是所有调用的硬总上限。
